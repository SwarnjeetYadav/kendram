# Local PostgreSQL + MongoDB Atlas staging setup

This guide is for **development/test data only** on Windows. It does not enable PostgreSQL-backed production traffic. Run commands from PowerShell in `backend/`.

## 0. Safety rules

- Use a dedicated local database named `anvaya_migration_staging`; do not point the importer at a production PostgreSQL database.
- Prefer a MongoDB Atlas **test/development database or sanitized cluster snapshot**. If only a shared/live cluster is available, do not run `--apply` against it; ask the project owner to make a sanitized copy first.
- Never paste either URI, database credentials, JWT secrets, or raw user records into chat, GitHub issues, commits, or screenshots.
- The importer currently handles **users only**. It is not a complete application-data migration.

## 1. Check local PostgreSQL

Install/start PostgreSQL locally and create a fresh database. In pgAdmin: connect to your local server, right-click **Databases → Create → Database**, and name it `anvaya_migration_staging`.

Or from PowerShell, if `psql` is on PATH and your local PostgreSQL role can create databases:

```powershell
createdb -h localhost -p 5432 -U postgres anvaya_migration_staging
```

If the database already exists, do not drop it blindly. Inspect it first and back it up before reusing it.

A typical local URI is:

```text
postgresql://postgres:<YOUR_LOCAL_PASSWORD>@localhost:5432/anvaya_migration_staging
```

Replace the placeholder locally. Do not commit the URI.

## 2. Prepare MongoDB Atlas access

1. In Atlas, choose the development/test cluster and database containing the test users.
2. Under **Database Access**, ensure a database user has the minimum read permissions needed for that source database.
3. Under **Network Access**, allow your current development IP. Avoid opening access to `0.0.0.0/0` just to make the migration work.
4. Copy the driver connection string and select the intended test database in the URI. Check the cluster and database name before running any command.
5. If the data is in a live/shared database, stop here and create a sanitized test copy instead.

## 3. Configure the terminal without putting secrets in shell history

Open PowerShell in the repository's `backend` folder. These prompts store the values in the current process environment; they are not written into source code.

```powershell
$env:MONGODB_URI = Read-Host "MongoDB Atlas TEST database URI"
$env:DATABASE_URL = Read-Host "Local PostgreSQL staging URI"
$env:JWT_SECRET = "local-only-change-this-to-a-long-random-test-secret"
```

The PostgreSQL target should resolve to `localhost:5432/anvaya_migration_staging`. Verify this in pgAdmin before applying any write. The URI itself may contain URL-encoded characters; use the exact driver URI generated by your provider.

## 4. Install dependencies and create the PostgreSQL schema

```powershell
npm ci
npm run db:migrate:postgres
```

This creates the schema only. If it fails, stop and fix the connection or migration error before importing records.

## 5. Dry-run the user import (read-only)

```powershell
npm run db:migrate:postgres:users
```

Expected behavior: JSON report with source user count, already-mapped count, planned inserts, and blockers. It should not include emails or password hashes. **Do not apply if blockers are present, counts are surprising, or you are uncertain which database is connected.**

## 6. Apply only to the local staging database

Only after verifying the source is test data, the target is the local staging database, and the dry-run is clean:

```powershell
$env:POSTGRES_IMPORT_TARGET = "staging"
$env:POSTGRES_IMPORT_CONFIRM = "true"
npm run db:migrate:postgres:users -- --apply
```

Then re-run the dry-run:

```powershell
npm run db:migrate:postgres:users
```

The repeat run should show the imported users as already mapped and zero planned inserts. If it does not, stop and investigate. The environment flags are guardrails, not automatic verification of the target host.

## 7. Validate counts locally

Use pgAdmin Query Tool on `anvaya_migration_staging`:

```sql
SELECT COUNT(*) AS postgres_users FROM public.users;
SELECT COUNT(*) AS mapped_users
FROM public.users
WHERE legacy_mongo_id IS NOT NULL;
SELECT COUNT(*) AS users_missing_password_hash
FROM public.users
WHERE password_hash IS NULL OR password_hash = '';
```

Compare the mapped-user count with the import report. A nonzero missing-password count may be valid for pre-seeded synthetic records, but investigate it before auth testing. Do not share query results containing personal data.

## 8. What is not complete

This script imports only user accounts and preserves the legacy Mongo ID bridge. Projects, project memberships/roles, boards/columns, tasks, labels, comments, dependencies, invitations, messages, notifications, and activity still require entity-specific migration and reconciliation. Do not enable these flags yet:

```text
POSTGRES_AUTH_ENABLED=false
POSTGRES_PROJECTS_ENABLED=false
POSTGRES_TASKS_ENABLED=false
VITE_POSTGRES_API_ENABLED=false
```

CI success verifies repository checks, not connectivity to your laptop or successful migration of your Atlas records. The actual import and validation must be run locally against the intended staging/test databases.
